PART 1

코드 리뷰 인터뷰란

면접관은 "버그를 몇 개 찾았나"보다 무엇을 먼저 보고, 어떻게 우선순위를 매기며, 어떻게 말하는가를 봅니다.

면접관이 실제로 평가하는 것

평가 항목보는 것좋은 신호
정확성 (Correctness)버그, 엣지 케이스, 예외 처리빈 입력·None·경계값·동시성을 스스로 떠올린다
언어 숙련도Pythonic한 관용구, 표준 라이브러리 활용"이건 collections.Counter로 한 줄"처럼 대안을 구체적으로 제시
설계 감각책임 분리, 결합도, 확장성, API 형태"이 함수는 I/O와 계산을 같이 해서 테스트가 어렵다"
성능 감각시간/공간 복잡도, 불필요한 복사, N+1"리스트 in 검사가 루프 안에 있어 O(n²)입니다 → set"
안정성/보안리소스 누수, 인젝션, 비밀정보, 역직렬화shell=True, pickle.loads, f-string SQL을 즉시 지적
테스트 가능성테스트 존재·품질, 의존성 주입"이 분기는 테스트가 없습니다. 이런 케이스를 추가하면…"
커뮤니케이션톤, 우선순위, 근거 제시Blocking vs Nit 구분, 질문형 코멘트, 칭찬도 포함
흔한 감점 요인 스타일(공백, 따옴표) 지적만 10개 하고 실제 버그를 놓치는 것. 스타일은 도구가 잡는다고 말하고 넘어가는 것이 오히려 시니어다운 태도입니다.

리뷰 진행 순서: 큰 것 → 작은 것

  1. 맥락 파악 (1~2분) — 이 코드의 목적은? 입력/출력은? 호출자는 누구? 모르면 질문한다.
  2. 정확성 — 로직 버그, 엣지 케이스(빈 값, None, 0, 음수, 유니코드, 대용량), 예외 경로.
  3. 안정성/보안 — 리소스 정리, 타임아웃, 재시도, 인젝션, 비밀정보 노출.
  4. 설계 — 함수/클래스 책임, 중복, 추상화 수준, 의존성 방향, 공개 API 형태.
  5. 성능 — 복잡도, 불필요한 반복/복사, I/O 패턴. (측정 없이 과도한 최적화 요구는 금물)
  6. 가독성/관용구 — 네이밍, Pythonic 표현, 타입 힌트, docstring.
  7. 테스트 — 무엇이 테스트되지 않았는가?
  8. 스타일 — 린터/포매터로 자동화 제안.
소리 내어 생각하기 (Think aloud)
"먼저 전체 흐름을 보고, 정확성 문제를 우선 보겠습니다. … 여기서 items가 비어 있으면 ZeroDivisionError가 납니다. 이건 blocking입니다."
마무리 요약 템플릿
"치명적 이슈 2개(X, Y), 설계 개선 1개(Z), 나머지는 nit입니다. 가장 먼저 X를 고쳐야 하는 이유는 …"
시간 배분
30분 인터뷰라면: 맥락 2분 → 탐색/코멘트 20분 → 우선순위 요약과 개선 코드 제시 8분.

좋은 리뷰 코멘트 작성법

심각도 라벨을 붙인다

  • [Blocking] 버그, 데이터 손실, 보안, 계약 위반 — 머지 전에 반드시 수정
  • [Suggestion] 설계·가독성 개선 — 이유와 함께 제안
  • [Nit] 사소한 취향 — 무시해도 됨
  • [Question] 의도 확인 — 비난이 아닌 질문
  • [Praise] 잘한 점 — 학습 효과와 신뢰를 만든다

구조: 관찰 → 영향 → 제안

"timeout이 지정되지 않았습니다(관찰). 원격 서버가 응답하지 않으면 워커가 무한히 대기합니다(영향). timeout=(3, 10)을 지정하고 재시도 정책을 두는 건 어떨까요?(제안)"

나쁜 코멘트
"이거 왜 이렇게 짰어요?"
"틀렸음."
"그냥 다 다시 쓰세요."
좋은 코멘트
"[Blocking] def add(item, bucket=[])는 기본값 리스트가 호출 간 공유되어, 두 번째 호출부터 이전 값이 섞입니다. bucket=None 후 내부에서 생성하는 패턴을 제안합니다."

"[Nit] for i in range(len(xs)) 대신 enumerate(xs)가 의도를 더 잘 드러냅니다."
Google eng-practices의 원칙
"완벽한 코드는 없다. 코드베이스의 전체 건강을 개선한다면 승인하라." — 사람이 아니라 코드에 대해 말하고, 이유를 설명하고, 해결책은 강요하지 말고 제시한다.

레벨별 기대치

Junior

  • 명백한 버그·예외 누락 발견
  • 가변 기본 인자, is/==, 순회 중 수정 같은 함정 인지
  • PEP 8 네이밍, 관용구 (enumerate, with, 컴프리헨션)
  • 파일·커넥션 닫기
  • 매직 넘버, 중복 코드 지적

Intermediate

  • 함수/클래스 책임 분리, 테스트 용이성
  • 예외 계층 설계, raise ... from, 로깅
  • 타입 힌트 품질 (Protocol, TypedDict, Optional 남용)
  • 제너레이터/이터레이터로 메모리 절감
  • 표준 라이브러리 (itertools, functools, collections, pathlib)
  • pytest fixture/parametrize, mock 위치

Expert

  • GIL·free-threading, asyncio 이벤트 루프 블로킹
  • 데코레이터/디스크립터/메타클래스 트레이드오프
  • __hash__/__eq__ 계약, MRO, __slots__
  • 성능 측정(cProfile), 메모리 모델, 자료구조 복잡도
  • 보안(역직렬화, 인젝션), 공개 API 하위 호환성
  • 패키징, 의존성, 관측성(observability)
포인트 같은 코드에서도 Junior는 "여기 버그"를, Expert는 "이 버그가 생길 수밖에 없던 설계 원인과 재발 방지책(타입, 테스트, 린트 규칙)"까지 말합니다.
